Alignment

Pascal wants to share an idea in Pi, investigate it without changing the repository, approve a concrete plan with a command or shortcut, and let an explicit state machine own implementation, checks, independent review, feedback, publication, and authorized merging.

The problem is that a long prompt describes intent but does not own permissions, cancellation, recovery, or proof that a step actually completed. The extension adds those boundaries while keeping the visible experience small.

Use cases and edges

  • Investigate an idea, identify scope and edge cases, and ask only about decisions that change the plan
  • Present CMO, FMO, and a ranked premortem, with the exact Planning footer
  • Replace a plan and invalidate approval for its previous digest
  • Start Implementation from a trusted operator command or shortcut, never from model prose
  • Execute ordered units with exclusive repository ownership, serialized file tools, small commits, and configured checks
  • Run a second pass and an independent read-only reviewer against the current Git revision
  • Fix valid findings within a bounded budget and repeat affected evidence
  • Deliver a single PR or an ordered linear stack when the selected delivery capability is available
  • Poll current checks and reviews while preserving and reconciling all unresolved findings across pushes
  • Merge only with run-specific authorization and fresh positive evidence
  • Return to Planning while work is active, without admitting new writes or leaving an unowned worker
  • Recover after reload, crash, branch navigation, missing credentials, or an uncertain external result

Scope

Include a Pi extension, controlled SDK jobs, one XState coordinator, a durable journal, deterministic Git and GitHub adapters, tests, and an isolated integration harness. Configuration names the allowed commands, skill sources, reviewer, budgets, and delivery policy.

Exclude a daemon, graphical dashboard, general workflow DSL, a parallel writer fleet, personal skill edits, production deployment, and automatic daily-driver installation. Arbitrary shell is not exposed to implementation workers. Stack capability failures pause explicitly; they do not silently become a large single PR.

CMO (current Mode of operation)

Pascal manually pastes Planning and Implementation prompts and supervises the transitions. The prompts specify useful behavior, but the host agent still controls tool use and reports progress in prose. A mode name alone cannot prove that writes are blocked, an agent stopped, a review covers the current commit, or a remote mutation already happened.

Happy path

  1. Load the extension in an isolated Pi session. Planning is the default
  2. Inject the supplied Planning instructions. Allow known read tools and a plan-recording tool
  3. Record plan text, writable scope, ordered units, required checks, and a content digest
  4. The operator runs /workflow implement or the shortcut to approve that exact digest. --merge separately grants eventual merge authority for this run
  5. Acquire exclusive ownership of the canonical repository/worktree. Preflight identity, cleanliness, the selected model, skill files, reviewer protocol and login, command-execution grants, and delivery configuration. Actual model access is established by its first request
  6. One SDK worker executes each unit with scoped edits. The coordinator verifies scope, creates a commit, runs authoritative checks against that clean committed tree, and confirms that checks did not change source content
  7. Run the configured second-pass skill, display the exact Codex command, then launch GPT-6 Astra high in read-only mode
  8. Validate findings, repair within the configured budget, and invalidate review and check evidence when HEAD changes
  9. Publish regular PRs through the selected single or linear-stack adapter. Record their exact repository, branch, base, head, and URL
  10. Observe current checks and reviews. Unknown, pending, failed, stale, or unresolved evidence cannot satisfy a gate
  11. With merge authority, recheck the remote head and required gates. The merge request itself includes the expected head SHA and respects server-enforced branch requirements. A moved head rejects the request. Otherwise deliver the PR unmerged
  12. Run the configured retrospective and report the outcome, uncertainty, and remaining decisions

Ownership and data

The machine owns finite modes and transitions. Context holds an immutable accepted plan, run-specific grants, unit position, operation receipts, and evidence. UI and tool policy derive their state from the machine. No second mutable mode registry exists.

Planning
  → preflight → work unit → commit → authoritative checks
  → second pass → external review → bounded repair
  → publish → monitor → merge gate → retrospective → delivered

Any active step → stopping → Planning, after confirmed drain
Any unresolved gate → blocked, with a typed reason
Restart → reconciliation, with effects closed

Modules own domain knowledge: Pi integration, workflow state, capability policy, worker lifetime, repository delivery, and validated journal data. They are not one file per temporal stage.

Permissions

Planning denies unknown tools, edit, write, arbitrary shell, nested bypass tools, and user-bash execution. Active tool declarations improve model behavior; a fail-closed tool_call guard supplies enforcement. Coordinator bookkeeping and the normal Pi transcript may persist, but model work cannot mutate repository files.

Implementation workers receive scoped read and file-edit tools. They receive no arbitrary shell, credential management, GitHub mutation, or self-approval tool. The coordinator owns checks, Git, and GitHub effects. Path admission checks canonical targets, symlinks, repository metadata, and writable scope. Each complete read-modify-write operation is serialized.

Configured checks execute repository code, including code the worker can edit. Their filesystem and network effects are an explicit trust boundary. The operator separately grants execution of those named commands and their stated effects; absent that grant, preflight blocks. Scoped file admission does not sandbox check scripts. An OS sandbox is required for users who need to constrain arbitrary repository code, and is outside this first version.

This is an enforced boundary for mediated file tools and owned jobs. It is not an operating-system sandbox against approved check scripts, arbitrary co-loaded extension JavaScript, or adversarial filesystem races. Supported execution uses controlled SDK resources without ambient extensions.

Cancellation, recovery, and uncertainty

Returning to Planning closes admission synchronously, requests cancellation, waits for SDK idle and owned process exit, then displays Planning. While draining, the visible state remains Stopping. Late results cannot advance another run. Local drainage cannot undo an already accepted remote action; retain uncertain intents, observe them, and report uncertainty before claiming a settled delivery outcome.

A versioned journal belongs to the repository and run, independently of conversation branches. Its coordinator metadata is untracked and excluded from worker editing. Acquire a cross-process ownership lock before effects. Record the owner and release only after drain. Reject a second live owner. Stale-owner recovery verifies that the owner is gone before acquiring ownership and reconciling; uncertainty blocks.

Store intent before an external mutation and an observed receipt afterward. On restart, inspect Git and GitHub before resuming. Never start restored effectful actors directly or replay PR creation or merging because a completion receipt is absent. Preserve dirty content after a crash. Explicit resume can accept attributable in-scope edits; unrelated or unattributable changes remain blocked. No reset, cleanup, or deletion hides them.

Preserve the causal phase and pending decision. Changed plan digests revoke approval. Changed heads invalidate affected evidence. Changed repository identity, missing capabilities, conflicts, exhausted budgets, and ambiguous observations produce a named blocked state. Persist outstanding review findings independently of the polling cursor. A new push must reconcile older unresolved findings, not discard them.

Linear-stack delivery

When selected, ordered units map to ordered branches. Each branch starts from the preceding unit's committed head. Publish PRs bottom-up against their actual dependent bases. Record and verify checks, independent review, and unresolved findings for every PR's base and head. The first release waits for all remaining layers before landing the contiguous verified prefix.

After an ancestor lands, reconcile each remaining base against the destination branch, retarget the next eligible PR, and refresh affected evidence. Use merge commits that preserve ancestry. Never force-push or silently rebase. Conflicts, unsupported server policy, or a required destructive history rewrite block with a concrete decision. A changed descendant head invalidates its previous evidence.
